# Hierarchical MapsとSpatial Context V3

ステータス: 提案中。メンテナーの承認後に実装可能です。

対象読者: プロダクト、デザイン、Marinara Engineのコントリビューター

置き換え対象: `hierarchical-locations-prd-v2.md`

## アーキテクチャの境界

この計画では、空間の把握を、状態の境界を狭く保った単機能として扱います。

この機能は階層マップと空間把握のシステムであり、Voxtaのような汎用シナリオエンジンではありません。Voxtaから借りるのは1点だけです。永続化した状態をもとに、小さく関連性の高いプロンプトコンテキストを選び出すという考え方です。当初はフラグ、変数、イベント、スクリプト、タイマー、行動推論用の別モデルを追加しません。

対応するオーナーモードはRoleplayとGameです。旧来の`visual_novel`という列挙値は互換性のために残っているだけで、製品としてサポートするモードではありません。

この計画は5つの層に分かれています。

| 層 | 役割 | 例 |
| --- | --- | --- |
| マップ定義 | 変化しない空間の事実 | 図書室は魔法使いの塔の中にある |
| ランタイム状態 | 現在のシーンのロケーション | 現在のシーンは図書室にある |
| プロンプトプロジェクション | 範囲を限定したモデルへの状況提示 | パンくずリスト、現在地の記憶、到達できる出口 |
| ビジュアルアイデンティティ | 場所ごとの参照画像(任意) | 図書室のアーチ、窓、素材がシーンをまたいで保たれる |
| 遷移 | 検証済みの状態変更 | 図書室から天文台へ移動する |

ステートマシンは意図的に小さく保っています。

```text
current location + requested destination + definition revision
                              ↓
                  validate ownership and reachability
                       ↙ accepted       rejected ↘
              persist snapshot         preserve state
```

まず手動での移動を出します。その後、`change_location({ destinationId })`のような制約付きのモデルツールから同じ遷移を要求できるようにするかもしれません。検証して適用するのはモデルではなくサーバーです。行動推論のための別呼び出しは、必要だという根拠が後から出てくるまで見送ります。

## 概要

RoleplayとGameで共有するHierarchical Map機能を追加します。この機能が提供するのは、制作者が定義したロケーションの階層、正となる焦点ロケーション1つ、範囲を限定した現在地のプロンプトコンテキスト、そしてサーバーが検証する移動です。

再利用できる世界の事実については、引き続きロアブックが正式な情報源です。階層側は安定したIDで既存のロアブックのエントリーを参照できるので、内容をコピーしたり書き換えたりせずに、現在のロケーションに関係するロアだけを選び出せます。AIによるマップの下書きでは、明示的に選んだロアブックを根拠となる素材として使えます。その際、出典のあるロケーションと、推測または創作で足したロケーションを区別しなければなりません。

ロケーションには、ビジュアルアイデンティティのキットを任意で持たせられます。短いビジュアルアンカーと、プロフィールギャラリーの画像への安定した参照の組み合わせです。ロケーションはあくまで空間の実体であり、画像ではありません。全体の描画スタイルはチャットの画像スタイルプロファイルが決め、ロケーションの参照が場所を保ち、キャラクターやペルソナの参照がそこにいる人物を保ちます。

連携したConversationは、後の段階でリンク先の物語のロケーションを安全な形で読み取れるようになりますが、空間の状態を所有することも変更することもありません。

```text
authoritative hierarchy + current location
                    ↓
resolve breadcrumb, context, and valid destinations
                    ↓
build the mode-specific prompt
                    ↓
commit a validated move with the next owner turn
                    ↺
```

これは汎用のシナリオエンジンではありません。フラグ、イベント、制作者が書くJavaScript、経路探索は追加しません。一方で、マップ表示、レイヤー表示、リスト表示を備えた、入れ子構造のビジュアルなマップブラウザーは含みます。

## プロダクトとしての決定事項

以下の決定により、V2で残っていた論点を解消します。

1. 階層の定義と現在のロケーションは別々に保存します。
2. 現在のロケーションは、確定したメッセージとスワイプの状態と一緒にスナップショットとして残します。これにより分岐、再生成、チェックポイントから正しい位置に戻せます。
3. 手動の移動は、次のオーナーモードのユーザーターンと一緒に、プロンプト生成の前に不可分に確定します。
4. Spatial Contextを有効にしているあいだは、これが唯一の正です。Gameの旧来の自由記述のロケーションが第2の正になってはいけません。
5. RoleplayとGameは1つの共有された空間プロジェクション契約を使い、モードごとの違いは薄いプロンプトアダプターで吸収します。
6. `awarenessSummary`は制作者が書きます。未記入の場合、Conversationは公開説明の抜粋だけを、長さを限って受け取ります。
7. 連携先のキャラクターがその場にいると正となるデータで示せない限り、Conversationはシーン全体を指す言い回しを使います。
8. 直接リンクと、子ロケーションのビジュアルな配置はMVPに含みます。
9. 既存のGameのグリッドマップとノードマップは、階層のロケーションに明示的に結び付けられます。名前による自動一致は行いません。
10. 再利用できる世界の事実の正典はロアブックが持ち、マップは空間としての同一性、包含関係、移動、現在地の状態を持ちます。マップのロケーションは安定したIDでロアブックのエントリーを参照し、その内容をコピーすることはありません。
11. ロケーションへの添付は、チャット単位で明示的に指定する発動元です。まさにそのロケーションが現在地であるあいだ、有効なエントリーはキーワードに一致しなくても発動できます。ただし無効化された、または明示的に除外されたロアブックとエントリーは無効のままです。
12. ロアブックを根拠にしたマップの下書きは、オーナー側のランタイムUIに従い、連携したConversationより先に実装します。出典のロアブックを選んだ場合、下書きは、根拠のない地理を正典として見せるのではなく、どのロケーションが出典付きで、どれが推測で、どれが創作かを示さなければなりません。
13. ロケーションが画像に置き換わることはありません。安定した画像IDで、任意のビジュアルアイデンティティ素材を参照できます。全景を示す主参照が1つと、数を限った補助参照です。
14. ロケーションのビジュアル参照は、対象となる画像生成の経路にだけ渡します。テキスト生成、ロアの発動、連携したConversationが画像のバイト列や画像専用のメモを受け取ることはありません。
15. 絵コンテは同じビジュアルリゾルバーの下流の利用者です。絵コンテはそれぞれ、メッセージとスワイプに紐づいた参照マニフェストを凍結するので、後から再生成しても新しいロケーションやキャラクターのアートが黙って混ざることはありません。
16. モデルからの移動要求は後の段階に回します。

## 使い勝手

### 制作

**Chat Settings**(チャット設定)には、Spatial Contextのコンパクトなセクションを表示します。内容は次のとおりです。

- 有効かどうか
- 現在のパンくずリスト
- ロケーション数と警告数
- **Open Location Editor**(ロケーションエディターを開く)の操作

エディターは狭い設定フォームではなく、遅延読み込みするマップの作業画面です。

- デスクトップでは、階層ペイン、ローカルマップまたはレイヤー表示、ロケーション詳細ペインを並べます。
- モバイルでは一度に1つのペインだけを表示し、戻る操作をはっきり示します。
- 検証結果は該当する欄やノードのすぐ横に出します。
- 保存状態とリビジョンの競合は常に見える状態にします。
- 削除の主操作はアーカイブです。完全削除は制限します。
- 選択するとロケーションをプレビューします。移動は別の**Enter**(入る)操作で行うので、クリック1つが確認、編集、移動のどれを指すのか曖昧になることはありません。
- 親はそれぞれ、子を座標付きのマップ、順序付きのレイヤー、アクセシブルなリストのいずれかで表示します。
- サブツリーの複製により、MVPの段階でチャットをまたぐテンプレートを用意しなくても、制作者が既存の構造を再利用できます。
- ロケーションにはそれぞれ、段階的に開く`Linked lore`セクションがあります。既存のロアブックのエントリーを検索でき、無効なものや見つからない参照も表示し、ロアの内容をコピーも削除もせずにOpen entryとDetachを行えます。
- ロケーションにはそれぞれ、段階的に開く`Visual identity`セクションがあります。主画像、補助参照、使いどころのメモに加えて、ギャラリー、アップロード、生成の操作を明示的に用意します。画像がロケーションの名前、アイコン、アクセシビリティー用の移動ラベルを置き換えることはありません。

### ロアブックを根拠にした下書き

AIマップビルダーは、オーナーのチャットで選択中または有効なロアブックがある場合に、ロアブックを根拠にする方法を提示します。この根拠付けは明示的で中身を確認でき、通常のキーワード走査とは異なります。

- Gameのセットアップでは、**Lorebooks**ステップで選んだロアブックをマップの出典のデフォルトにします。
- Roleplayでは、開いているチャットの有効なロアブックをデフォルトにしたうえで、マップビルダーの中で出典の選択を変更できます。
- `Strict canon`では、名前の付いたノードをすべて、選択したロアのエントリー1つ以上から作ります。根拠のないつなぎの場所を創作するのではなく、出典のある根が複数あればそのまま複数残します。
- `Canon with expansion`では、出典のある名前と関係を保ったうえで、実用上の隙間を埋めるために、推測または創作だとはっきり分かる形でロケーションを足せます。
- `Setup only`はこれまでの動作を保ち、ロアブックの根拠付けなしで、セットアップ、世界の概要、物語の筋書き、シナリオ、キャラクターの情報を使います。
- 選択したロアブックがある場合は、`Canon with expansion`を扱いやすいデフォルトにします。ロアブックを作り込んでいる制作者のために、ビルダーは`Strict canon`を1操作の場所に置いておきます。

下書きのプレビューでは、生成されたノードにそれぞれ`Lore-backed`、`Inferred`、`Added by AI`のいずれかを表示します。`Lore-backed`のノードは出典のエントリーを一覧し、Open entryを提供します。このラベルが示すのは有効な出典参照があることであって、モデルが文章を正しく解釈したことではありません。意味が合っているかを判断する権限は制作者のレビューに残ります。Applyが変えるのはローカルの作業用コピーだけで、永続化の境界は引き続きSaveです。

### ロケーションのビジュアルアイデンティティと参照画像

ロケーションの画像は、階層をギャラリーや第2の空間の正に変えることなく、シーンの一貫性を高めるためのものです。

- 制作者は、画像をアップロードする、既存のプロフィールギャラリーの画像を選ぶ、生成されたシーンを昇格させる、あるいはロケーションのパンくずリスト、公開説明、ビジュアルアンカー、紐づくロア、選択中の画像スタイルプロファイルから全景の参照画像を生成する、のいずれかを行えます。
- チャットギャラリーの画像、生成されたGameの背景、その他の一時的な素材を添付する場合は、まずプロフィールギャラリーに永続的な素材を作ります。マップが保存するのは安定したギャラリー画像IDだけで、ファイルパス、外部URL、base64のデータは保存しません。
- `identity`の画像は1つだけ主画像にできます。補助画像には、特徴的なディテール、別アングル、間取り、継承できる画風の手がかりなどを持たせられます。
- `layout`の参照は、背景や間取り図を明示的に求めるリクエストでない限り、エディター内の補助にとどめます。構図を崩すおそれがあるため、通常のシーン挿絵には自動で送りません。
- 子孫への継承を選べるのは`style`の参照だけです。identityとdetailの画像はそのロケーションだけに適用されるので、街のスカイラインが中のすべての部屋のビジュアルアイデンティティとして黙って使われることはありません。
- 生成されたシーンのアートが自動で正典になることはありません。`Set as location reference`は明示的なレビュー操作なので、生成を繰り返すうちに偶然のディテールや画風のずれが増幅されることを防げます。
- 選択中のロケーションのインスペクターには、主画像と参照の役割を表示します。情報密度の高い階層表示やマップ表示は名前を優先し、余白があれば小さなサムネイルを添えることはありますが、移動が画像の見分けに依存することはありません。
- 画像生成のプレビューには、解決されたロケーションとキャラクターの参照、その役割、プロバイダーの上限で除外された参照をすべて表示します。診断情報に生のbase64を記録したり表示したりすることはありません。

想定している一貫性の重ね方は次のとおりです。

```text
chat image style profile  -> shared rendering language
current location refs     -> stable architecture and place identity
character/persona refs    -> stable people and appearance
scene prompt              -> current action, framing, weather, and lighting
```

参照画像はあくまで見た目の手がかりであり、自動的にロアになるものではありません。画像を足してもロケーションは作られず、包含関係も変わらず、ロアブックの事実も書き込まれません。画像からマップを推測する仕組みは、別途レビューする将来の作業に残します。

### 絵コンテの参照の継続性

絵コンテは、完了したGMターンのレビュー済みビジュアルアイデンティティを受け取ります。ただし、空間機能そのものが絵コンテに依存してはいけません。

- プロフィールギャラリーと各エンティティーのギャラリーは参照バンクを形作り、1つのロケーション、キャラクター、ペルソナに対して複数のレビュー済み画像を持てます。生成されるキーフレームが受け取るのは、そのバンクから選ばれた、プロバイダーの上限に収まる分だけです。
- 絵コンテを作ると、その元メッセージとスワイプに対応する空間スナップショットを厳密に解決します。過去のターンにチャットの最新ロケーションを当てはめることはありません。
- 絵コンテは、解決したロケーション、順序付きの候補画像ID、キーフレームごとの選択と除外、プロバイダーの許容量を、ビジュアル参照マニフェストとして凍結します。再生成では、制作者が明示的に`Refresh references`を選ぶまでそのマニフェストを再利用します。
- 主となるロケーションの候補は、どのキーフレームからも使えます。キャラクターとペルソナの候補はフレームごとの登場キャラクターの一覧によって変わるので、画面に映らない出演者が参照の枠を消費することはありません。
- 最初のバージョンでは、描かれるエンティティーごとに主画像を1つ、加えて補助のロケーション画像を最大1つ自動で選びます。参照バンクが充実していれば手動選択や、将来のショットを意識したアングル、衣装、表情、ディテールの一致に役立ちますが、Marinaraが保存済みの画像をすべて毎フレーム送ることはありません。
- 自動の枠が1つしか残っていない場合、登場キャラクターのいるキーフレームは主要な登場キャラクターを選び、登場キャラクターのいない全景のキーフレームは主となるロケーションを選びます。枠が2つ以上あるときは、追加の登場キャラクター参照より先に主となるロケーションを選びます。
- 許容量の大きいプロバイダーに変えても、既存の絵コンテに参照が黙って足されることはありません。許容量の小さいプロバイダーの場合は、凍結したペイロードを黙って書き換えるのではなく、インラインで`Review references`の競合を出します。
- キーフレームのプレビューにはそれぞれ、段階的に開く`Visual sources`が1つあり、解決されたロケーション、選ばれたキャラクター、画像の役割、順序、除外の理由を一覧します。`Refresh references`もその場から使えるので、絵コンテ専用の素材管理画面や操作をさえぎるウィンドウを別に用意する必要はありません。
- 生成されたキーフレームが自動でキャラクターやロケーションの参照になることはありません。永続化の境界は、既存の明示的な昇格操作だけです。

### 実行中の移動

オーナーモードのチャット画面には次を表示します。

- 保存済みの現在のパンくずリスト
- 有効な移動先の選択
- はっきりラベル付けされた保留中の移動先

移動先を選んだだけでは、正となる状態はすぐに変わりません。次のメッセージを送信すると、表示されるメッセージ本文とは別に、移動先IDと想定リビジョンを送ります。サーバーは返信用のプロンプトを組み立てる前に移動を確定します。

検証に失敗した場合、メッセージと移動が中途半端に確定することはありません。クライアントは下書きを保持し、競合の内容を説明します。

## データモデル

定義はチャットのメタデータに置きます。実行中の位置はスナップショットの履歴に置きます。

```ts
export type SpatialOwnerMode = "roleplay" | "game";

export type LocationVisualReferenceRole = "identity" | "detail" | "layout" | "style";

export interface LocationVisualReference {
  imageId: string;
  role: LocationVisualReferenceRole;
  primary?: boolean;
  usageNote?: string;
  inheritToDescendants?: boolean;
  sortOrder: number;
}

export interface ChatLocation {
  id: string;
  name: string;
  parentId: string | null;
  description: string;
  kind: "region" | "settlement" | "place" | "building" | "floor" | "room";
  modelMemory?: string;
  icon?: string;
  childPresentation: "map" | "layers" | "list";
  placement?: { x: number; y: number };
  layerOrder?: number;
  awarenessSummary?: string;
  visualIdentity?: string;
  visualReferences: LocationVisualReference[];
  lorebookEntryIds: string[];
  links: ChatLocationLink[];
  status: "active" | "archived";
  sortOrder: number;
}

export interface ChatLocationLink {
  targetId: string;
  label?: string;
  bidirectional: boolean;
  state: "available" | "hidden" | "blocked";
}

export interface SpatialContextDefinition {
  schemaVersion: 1;
  ownerMode: SpatialOwnerMode;
  enabled: boolean;
  locations: ChatLocation[];
  startingLocationId: string | null;
  revision: number;
}

export interface SpatialContextSnapshot {
  id: string;
  chatId: string;
  messageId: string;
  swipeIndex: number;
  currentLocationId: string | null;
  definitionRevision: number;
  createdAt: string;
}

export interface PendingSpatialTransition {
  destinationId: string;
  expectedDefinitionRevision: number;
  expectedCurrentLocationId: string | null;
  commandId: string;
}
```

`SpatialContextDefinition`の中に`ownerChatId`を保存しないでください。所有者は、それを含んでいるチャットです。安定した不透明なIDは、名前の変更や親の付け替えを経ても壊れません。

最初のオーナーMVPでは、`lorebookEntryIds`や`visualReferences`の項目がない場合を空配列として扱います。これにより、後のパッケージが既存の定義を先回りして書き換えなくても、スキーマバージョン1を拡張できます。エントリーの参照と画像の参照は安定したIDだけです。ロアブック名、エントリー名、キー、内容、画像のパス、画像のバイト列は使うときに解決するもので、空間の定義にコピーすることはありません。`imageId`は永続的なプロフィールギャラリーを通して解決します。一時的な画像やチャット単位の画像を添付する場合は、先に永続的なコピーへ昇格させます。

## グラフの規則

有効な移動先は、次のうちアクティブなものです。

- 現在のロケーションの子
- 現在のロケーションの親
- 直接リンクの対象
- 双方向リンクの逆方向の対象

兄弟どうしが自動的に隣接することはありません。

次の場合は拒否します。

- IDの重複
- 親またはリンク対象が存在しない
- 自分自身を親にする、または親のループ
- ロケーションが500を超える
- 深さが20を超える
- 1ロケーションあたりのリンクが50を超える
- 1ロケーションあたりのロアブックエントリー参照が50を超える
- 1つのロケーションでロアブックエントリー参照が重複している
- 1ロケーションあたりのビジュアル参照が6を超える
- 1つのロケーションでビジュアル画像の参照が重複している
- 主となるビジュアル参照が2つ以上ある、または主参照の役割が`identity`ではない
- `style`以外の役割で子孫への継承が指定されている
- 配置座標が0から100の範囲外
- レイヤーの親の中でレイヤー順序が不正または重複している
- アーカイブ済み、非表示、通行不可、到達できないロケーションへの移動
- リビジョンが古い、または現在のロケーションが変わっている
- 同じコマンドIDが異なる内容で再利用されている
- Conversationからの変更操作

テキストの上限は次のとおりです。

- 名前: 200文字
- 説明: 4,000文字
- 認識用の要約: 1,000文字
- モデル向けの非公開の記憶: 8,000文字
- ビジュアルアイデンティティ: 800文字
- ビジュアル参照の使いどころのメモ: 300文字

直接リンクのループは有効です。親のループは無効です。

### アーカイブと削除

- 現在のロケーションまたは開始ロケーションをアーカイブする前に、不可分な差し替えが必要です。
- アクティブな子を持つロケーションはアーカイブできません。
- 完全削除ができるのは、入ってくるリンクのないアーカイブ済みの末端ロケーションだけです。
- 子孫が黙って別の親に付け替えられることはありません。
- 見つからないロアブック参照は、グラフの破損ではなく警告として扱います。
- ロケーションをアーカイブしたり削除したりしても、参照先のロアブックのエントリーは削除されません。
- ロアブックやエントリーを削除しても、マップが黙って書き換えられることはありません。ロケーションには修復できる壊れた参照が残り、制作者が切り離すか差し替えるまでそのままです。
- ロケーションをアーカイブしたり削除したりしても、共有のプロフィールギャラリー画像は削除されません。
- ロケーションや凍結済みの絵コンテのマニフェストからまだ参照されているギャラリー画像は、制作者がその参照を切り離すか、依存するすべてのマニフェストを更新するまで削除できません。見つからない画像の参照は修復できる警告のままで、生のパスにフォールバックすることはありません。

## 永続化と履歴

### 定義

`SpatialContextDefinition`は`chat.metadata.spatialContext`に保存します。定義の更新には`expectedRevision`が必要で、受け入れられた更新はリビジョンを1つ進めます。

### 実行中の位置

現在の位置は、既存のGame Stateスナップショットの方式に従い、メッセージとスワイプで参照できるスナップショットとして保存します。

- 新しいオーナーチャットは`startingLocationId`から始まります。
- 確定したターンでは、受け入れられた移動の後にスナップショットを作ります。
- 再生成では、その結果のスワイプに位置を紐づけます。
- スワイプを切り替えると、対応するスナップショットを解決します。
- あるメッセージで分岐させると、その時点で有効だったスナップショットをコピーします。元のチャットの最新の位置ではありません。
- Gameのチェックポイントは、該当する空間スナップショットを参照するか、その内容を含みます。
- 再読み込みでは、最後に確定したスナップショットを解決します。

MVPでは、通常のメッセージ分岐によって定義の編集が巻き戻ることはありません。分岐は現在の定義のコピーを受け取り、以後は独自のリビジョン履歴を持ちます。実行中の位置は分岐点のものになります。

## プロンプトプロジェクション

サーバー側の共有プロジェクションサービスが、構造化されたプロジェクションのデータを解決します。薄いモードアダプターが、それを最終的なプロンプト文へ変換します。

### オーナー向けの物語プロジェクション

含めるもの:

- パンくずリストの名前
- 現在のロケーションID
- 公開説明
- 現在のロケーションのモデル向け非公開の記憶
- 移動できる先の名前、ID、リンクのラベル
- 状態が正であることを伝える指示

除外するもの: 無関係なロケーションの説明と記憶、非表示または通行不可の移動先、キャンバスの座標、エディター用のメタデータ。

### 現在のロケーションによるロアの発動

オーナー用の空間リゾルバーは、通常の空間プロジェクションと並べて、まさに現在のロケーションの`lorebookEntryIds`を返します。フォーマッターがそのIDやエントリーの内容を空間ブロックに貼り付けることはありません。代わりに、プロンプトの組み立て時にIDを既存のロアブック処理へ渡し、発動元`current_location`の強制候補として扱います。

規則:

- 最初のリリースでは、まさに現在のロケーションだけが添付されたロアを発動します。親や子孫がエントリーを暗黙に継承することはありません。
- ロケーションへの明示的な添付があれば、そのロアブックがグローバル、キャラクター連携、ペルソナ連携、チャットへの固定のいずれでもなくても、有効なエントリーを発動できます。
- 全体で無効化されたロアブック、無効化されたエントリー、チャットでの明示的な除外は、常に添付より優先されます。
- 既存のロアブックのマクロ、挿入位置、再帰、順序、ロアブックごとのトークンとエントリーの上限はそのまま使います。
- ロケーションに添付されたロアには、オーナープロンプト1回あたり合計2,048トークンの予約上限もあります。切り詰めは決定的で、Active Contextに表示します。
- ロケーションと、通常のキーワード、意味的一致、再帰、常時の規則の両方で発動したエントリーは1回だけ挿入され、発動元をすべて報告します。
- 確定した移動では、オーナーの返信プロンプトを組み立てる前に移動先のエントリーを解決します。保留中や拒否された移動がロアの発動を変えることはありません。
- Gameでは、そのロケーションをパーティーの正となる位置として言い表します。Roleplayでは焦点となるシーンとして扱い、すべてのキャラクターがその場にいるとは推測しません。

Active ContextのUIは、これらのエントリーを`Current location`にまとめ、所属するロアブック、発動元、トークンの使用量または切り詰め、Open entryを表示します。壊れた参照、無効な参照、除外された参照はマップエディターでは見えたままですが、プロンプトに入ることはありません。

### 連携したConversationのプロジェクション

Phase 3で追加します。含めるのは次だけです。

- リンク先の物語の名前とモード
- パンくずリスト
- `awarenessSummary`、またはその代わりに長さを限った公開説明の抜粋
- 読み取り専用であることを伝える指示
- 正となる状態で示せる場合に限り、キャラクターがその場にいること

モデル向けの非公開の記憶、内部ID、非表示の移動先、階層の全体、ロケーションに添付されたロアブックのIDと内容、ロケーションのビジュアル参照ID、ビジュアルアイデンティティのメモ、使いどころのメモ、画像のパス、画像のバイト列は、いずれも含めません。

Gameは、確定した`presentCharacters`の状態でその場にいることを示せます。Roleplayは、明示的な在席情報を持つまでは「The linked story's current scene is…」のような中立的な言い回しを使います。キャラクター名から在席を推測してはいけません。

### 必須のプロンプト経路

同じプロジェクションリゾルバーが、次のすべてに供給しなければなりません。

- Roleplayの生成
- GameのGM生成
- ドライラン(dry run)のプレビュー
- 実行時のPeek Promptの組み立て

キャッシュされたPeek Promptは、実際に送信したプロンプトをそのまま表示し続けます。デバッグログには最終的なプロジェクションを含めますが、通常のログレベルでモデル向けの非公開の記憶を記録してはいけません。

### 画像生成向けの現在ロケーションのビジュアルプロジェクション

ビジュアル参照は、物語用プロンプトとは別のリゾルバーを使います。このリゾルバーは、チャットの最新のロケーションではなく、その画像の対象に対応する空間スナップショットを解決します。Gameの自動アート生成では、そのアシスタントメッセージに対して確定したスナップショットを使います。過去のスワイプのアートを生成し直す場合や、過去のメッセージからIllustratorを呼び出す場合は、そのメッセージとスワイプで解決されたロケーションを使います。

対象となる経路は、Gameの自動シーンアート、Gameの手動シーン挿絵、そしてチャットごとのロケーション参照の設定が有効なときのRoleplayのIllustratorによるシーン生成と背景生成です。ポートレート、自撮り写真、アバター、スプライトの生成にロケーション参照が自動で付くことはありません。

チャットのメタデータには、既存のアバター参照の設定と対になる2つの設定があります。`illustratorUseLocationReferences`と`gameImageUseLocationReferences`です。値がない場合とfalseの場合は、後方互換のためオフとして扱います。制作者が最初の主ロケーション画像を設定すると、同じSaveの流れで`Use this location in scene art`を提示します。デフォルトでチェック済みですが同意は明示的なので、マップエディターに画像が表示されているというだけで画像のバイト列がプロバイダーへ送られることはありません。

候補の順序は決定的で、プロバイダーの制約も考慮します。

1. その画像リクエストのために明示的に選ばれた参照。
2. 解決されたロケーションそのものの主`identity`参照。
3. 参照されているキャラクターとペルソナを、シーンの順序で。
4. そのロケーションの補助的な`identity`と`detail`の参照を`sortOrder`の順で。
5. 最も近い祖先の、継承可能な`style`参照。

兄弟ロケーションや名前によるフォールバックは認めません。通常のシーンのリクエストで候補になるロケーション画像は最大2つで、そのうえで既存のプロバイダーアダプターが画像全体の上限を適用します。明示的なリクエスト参照が常に先に枠を使います。残る自動の枠については、背景のリクエストではキャラクター参照よりロケーションの同一性を優先し、挿絵では追加のキャラクター参照より先に主となるロケーション参照を選びます。プロバイダーが場所と要求されたキャラクターのすべてを受け取れない場合、プレビューは決定的なトレードオフと除外の理由をすべて報告します。

画像プロンプトのコンパイラーは、ロケーションのパンくずリスト、長さを限った`visualIdentity`、選ばれた各参照の長さを限った`usageNote`を追加します。スタイルの権限はチャットで選択中の`ImageStyleProfile`に残ります。参照画像は場所や被写体の同一性を保つためのもので、プロファイルのスタイル文、ポジティブタグ、ネガティブタグ、プロンプトモードを黙って置き換えてはいけません。

参照の役割は制作者の意図と選択の優先度を表すもので、すべてのプロバイダーが画像をidentity、detail、layout、styleとして解釈することを保証するものではありません。プロバイダーの対応状況の注記と生成プレビューにより、見た目を判断する権限は制作者に残ります。

テキストモデルへのリクエストは、これらの画像のバイト列も画像専用の使いどころのメモも受け取りません。連携したConversationは、ビジュアル参照のIDも内容も受け取りません。画像のデバッグログには画像ID、ロケーションID、役割、選択理由、除外を含めてかまいませんが、base64やファイルシステムのパスは決して含めません。

### 絵コンテのビジュアル参照マニフェスト

絵コンテのアダプターは、完了したGMターンについて、そのメッセージとスワイプが確定した後に、ビジュアル候補を一度だけ解決します。そして凍結したバンクと、キーフレームごとに選ばれたプロバイダー向けのペイロードを保存します。これにより、永続的な参照の同一性と、ごく一部しか受け取れないかもしれないプロバイダーへのリクエストを切り分けられます。

選択は決定的です。

1. 明示的なキーフレームの参照が先に枠を使います。
2. 自動の枠が1つ残っている場合、全景のフレームはロケーションの主参照を選び、登場キャラクターのいるフレームは主要な登場キャラクターを選びます。
3. 自動の枠が2つ以上残っている場合、まずロケーションそのものの主参照を選び、次に登場するキャラクターとペルソナの主参照を物語の順に1つずつ選びます。
4. 残りの容量は、そのロケーションの補助的な`identity`または`detail`を1つ、次に副次的な描画対象の参照、最後に最も近い継承可能なロケーションの`style`に使います。

絵コンテが暗黙にコンタクトシートや合成参照を作ることはありません。そうした手法はプロバイダーの解釈を変えうるため、プロバイダーごとの将来の最適化として残します。画像が見つからない、プロバイダーが変わった、プロバイダーの上限が減ったといった場合、マニフェストは`needs_review`になります。別のエンティティーを黙って選ぶことはありません。容量が増えた場合も、`Refresh references`が確認されるまで凍結したペイロードを保ちます。

マニフェストが保存するのは、ID、ラベル、役割、順序、選択理由、除外、元メッセージとスワイプ、解決されたロケーションID、定義のリビジョン、プロバイダーの識別情報、使用した参照の上限です。画像のバイト列やファイルシステムのパスは保存しません。デバッグ出力でそのマニフェストを説明してもかまいませんが、通常の画像生成と同じくbase64とパスは出力しません。

## Gameとの互換性

既存のGameのグリッドマップとノードマップは、引き続きローカルまたは戦術的な表現です。階層はその上に立つ世界と包含の層になります。

Spatial Contextが有効なとき:

- プロンプトに渡す正となる名前付きロケーションはSpatial Contextが供給します。
- Gameのトラッカーは、ロケーションとして空間のパンくずリストを表示します。
- 旧来のモデルからの修正や手動の修正が、自由記述のGameのロケーションを単独で変更することはできません。
- `GameMap.spatialLocationId`により、マップ全体を1つの階層ロケーションに結び付けられます。
- `GridCell.spatialLocationId`と`MapNode.spatialLocationId`により、入れる移動先を結び付けられます。
- 結び付けには安定したIDだけを使います。名前による自動一致は行いません。
- 結び付けられた移動先を選ぶと、階層ブラウザーと同じ保留中の遷移が作られます。
- 結び付けられていないセルやノードの間を移動しても、変わるのは戦術上のパーティー位置だけです。
- ロケーションに入ると、それに結び付いたローカルマップが選ばれることがあります。出るときは、最も近い結び付けられた祖先のマップが選ばれることがあります。

無効のときは、既存のGameのロケーションの動作は変わりません。

この境界により、現在のマップUIとセーブデータを保ちながら、名前付きの空間の正が2つ生まれることを防げます。

## APIの形

```text
GET  /api/chats/:chatId/spatial-context
PUT  /api/chats/:chatId/spatial-context
```

定義の更新:

```ts
interface UpdateSpatialContextRequest {
  expectedRevision: number;
  expectedCurrentLocationId: string | null;
  replacementCurrentLocationId?: string | null;
  definition: SpatialContextDefinition;
}
```

`replacementCurrentLocationId`を使うのは、定義の編集で実際の現在のロケーションをアーカイブする場合だけです。サーバーは、定義のリビジョン更新と同じ書き込みの中でその差し替えを検証して適用しなければなりません。通常の移動は引き続きオーナーモードのターン送信を通します。

保留中の移動は、即時遷移用の別エンドポイントではなく、既存のオーナーモードのターンリクエストで送ります。

サーバーは、定義の整合性、オーナーモード、想定リビジョン、想定される現在のロケーション、到達可能性、コマンドの冪等性を、メッセージ送信と同じトランザクションの中で検証します。

状態が古い場合は`409 Conflict`を、グラフや移動先が不正な場合は`400 Bad Request`を返します。エラーが非表示の移動先を明かしてはいけません。

## 実装計画

### Phase 0: 共有コアと検証用フィクスチャ

- 共有の型とZodスキーマを追加します。
- 純粋なグラフ検証、パンくずリスト、移動先のヘルパーを追加します。
- 有効なグラフと無効なグラフの決定的なフィクスチャを追加します。
- RoleplayとGameについて、メッセージとスワイプのスナップショットの統合点を確認します。
- 代表的なプロンプトプロジェクションの大きさを測定します。

完了条件: スキーマ、移動の意味づけ、スナップショットの挙動が、UIなしで実証されていること。

### Phase 1: オーナーMVP

1. 楽観的並行制御を伴う定義の永続化を追加します。
2. 空間スナップショットの保存と解決を追加します。
3. 不可分な保留中の移動を、オーナーモードのターン送信に組み込みます。
4. 再読み込み、スワイプ、分岐、Gameのチェックポイントに対応します。
5. 共有プロジェクションサービスを、必要なすべてのプロンプト経路に追加します。
6. コンパクトな設定セクション、階層ナビゲーター、ローカルマップのキャンバス、レイヤー選択、エディターの作業画面を追加します。
7. パンくずリスト、移動先の選択、プレビュー、保留状態をオーナー側の画面に追加します。
8. 既存のGameのマップ、セル、ノードを安定したロケーションIDで結び付けます。
9. 有効なときにGameのトラッカーのロケーションを整合させます。

完了条件: RoleplayとGameが同じ空間モデルから、制作、移動、保存、復元、プロンプト生成を行えること。結び付けられたGameマップの移動と、結び付けのない戦術移動が区別されたままであること。

### Phase 2A: ロケーションとロアブックの結び付けとランタイム

- ロケーションに`lorebookEntryIds`を追加し、互換性のデフォルトを空配列にします。
- ロケーションエディターに、インラインの添付、開く、切り離す、無効、除外、壊れた参照の各状態を追加します。
- まさに現在のロケーションの参照を、既存のロアブック処理を通して強制候補として解決します。
- 通常のマクロ、挿入、再帰、順序、ロアブックごとの上限を再利用します。加えて決定的な重複排除と、ロケーションロア合計2,048トークンの上限を追加します。
- Active Contextで、キーワード、意味的一致、再帰、常時のいずれの発動元とも並べて`current_location`を報告します。
- 移動、再読み込み、再生成、スワイプ、分岐を含めて、RoleplayとGameで挙動が同一であることを実証します。
- 連携したConversationがロケーションロアのIDも内容も受け取らないことを実証します。

完了条件: 制作者が既存のロアを明示的にロケーションへ結び付けられ、オーナープロンプトでは受け入れられた現在のロケーションだけがそれらのエントリーを発動すること。

### Phase 2B: ロアブックを根拠にしたマップの下書き

- 作成、置き換え、履歴を壊さない拡張の各リクエストに、グラウンディングのモードと、明示的なロアブックまたはエントリーの出典選択を追加します。
- キーワードの発動や生成された世界の概要に頼らず、この制作操作のために、選択された有効なロアのエントリーを直接読みます。
- 接続の制約を踏まえた、範囲を限った出典カタログを作ります。除外件数が見え、順序は決定的にします。
- モデルには一時的な出典キーを渡し、返ってきたキーをすべてサーバー側で検証し、永続化するのは安定したエントリーIDだけにします。
- `setup_only`、`lore_strict`、`lore_expand`の動作を、プレビューでの出典表示とあわせて実装します。
- 有効な出典エントリーを生成されたロケーションへ自動で結び付けつつ、ApplyとSaveは別々のレビュー境界として保ちます。
- 追加のみの拡張では、既存のロケーションIDとロアの結び付けをすべて保ちます。

完了条件: ロアブックを使いこなす制作者が、選んだ正典を直接の根拠としたマップを生成し、根拠のない追加をすべて見分け、永続化の前に却下または編集できること。

### Phase 2C: ロケーションのビジュアルアイデンティティとシーン参照

- 長さを限った`visualIdentity`と`visualReferences`の項目を、空の互換性デフォルト付きで追加します。
- 永続的なプロフィールギャラリーの画像IDと、既存の安全なギャラリーのアップロード、メタデータ、画像生成の経路を再利用します。定義に生のパス、外部URL、base64を保存してはいけません。
- チャットごとのIllustratorとGameのロケーション参照の設定を、対になる形で追加します。最初の主画像を設定するSaveの流れで、プロバイダーへの送信を有効にする前に明示的な同意を得ます。
- 全景の参照画像は、範囲を限ったそのロケーションの情報と、有効な添付ロアだけから生成します。無関係なロアブックや階層の枝を走査してはいけません。
- ロケーションエディターに、インラインの主画像、補助、役割、使いどころのメモ、ギャラリー選択、アップロード、生成、切り離し、壊れた参照、被参照の各状態を追加します。
- 対象となるGameとRoleplayのシーンアートのリクエストで、そのメッセージとスワイプに対応する厳密なロケーションを解決し、ロケーション、キャラクター、ペルソナ、明示的な参照をプロバイダーごとの上限のもとで統合します。
- 生成されたアートに、明示的な`Set as location reference`の昇格操作を追加します。生成されたシーンを自動で昇格させてはいけません。
- 分岐とJSONLメタデータのエクスポートを通してビジュアル参照IDを保ち、移行先に素材がない場合は警告し、プロファイルのバックアップと復元に素材を含めます。
- 物語のプロンプトと連携したConversationが、ロケーション画像のID、バイト列、パス、画像専用のメモのいずれも受け取らないことを実証します。

完了条件: 制作者が場所の見た目を確立し、レビュー済みの同一性を再利用したシーンを複数生成でき、どのビジュアル参照が送られたかを正確に確認でき、空間やロアの正を変えずにその参照を削除または差し替えられること。

### Phase 2D: 絵コンテのビジュアル参照マニフェスト

- 空間の永続化を絵コンテに結び付けるのではなく、Phase 2Cのビジュアルリゾルバーの周りに下流の絵コンテアダプターを追加します。
- 元メッセージとスワイプの空間スナップショットを解決し、そのうえでロケーションとエンティティーの参照バンク、およびキーフレームごとのプロバイダー向けペイロードを凍結します。
- 容量が許す限り、ロケーションそのものの主参照をキーフレーム間で再利用しつつ、キャラクターとペルソナの参照は各フレームの登場キャラクターの一覧から選びます。
- 再生成を再現可能にするため、プロバイダーの識別情報、参照の許容量、順序付きの選択、除外の理由を永続化します。
- 絵コンテのプレビューと再生成に、インラインの`Visual sources`、`Review references`、明示的な`Refresh references`の各状態を追加します。
- 画像が見つからない場合やプロバイダーの許容量が縮んだ場合に、黙って選び直すことを拒否します。新たに空いた容量を自動で埋めてはいけません。
- 既存の絵コンテのライフサイクルを通してマニフェストを保ち、キーフレームから動画への変換が引き続き、描画済みのキーフレームだけを最初のフレームの入力として使うことを実証します。

完了条件: どの絵コンテのキーフレームも、自分のビジュアル入力を説明でき再現できること。繰り返し現れるフレームが当時の正しい場所の同一性を共有すること。プロバイダーの制限がロケーションや描かれる人物を黙って入れ替えないこと。

### Phase 3: 連携したConversation

- 生成時に`connectedChatId`を通して最新のオーナー状態を解決します。
- 範囲を限った読み取り専用のプロジェクションを追加します。
- 在席については控えめな言い回しを使います。
- オーナーモードの生成が使っている場合でも、ロケーションに添付されたロアのIDと内容、ビジュアル参照のIDとメタデータ、画像のパス、画像のバイト列は除外します。
- リンク解除、再リンク、オーナーの削除、壊れたリンク、完結した物語、ロケーションロアのネガティブコントロールを網羅します。

### Phase 4: モデルからの移動要求

- オーナーモード向けに、型付きの`change_location`リクエストを追加します。
- リビジョン、到達可能性、冪等性の検証を同じように適用します。
- 受け入れた要求と拒否した要求をデバッグ診断に記録します。
- Conversationは引き続き遷移を要求できません。

### Phase 5: 制作者向けテンプレート

- 再利用できるロケーションのサブツリーやマップ全体を保存し、インポートできるようにします。
- 所有関係と統合の挙動を定めたうえで、制作者がキャラクターと一緒に初期マップを配布できるようにします。
- 別のチャットへコピーするときは、新しいIDを振りつつ内部の参照関係を保ちます。

| 論点 | 現在のリポジトリーの挙動 | 実装への影響 |
| --- | --- | --- |
| 定義の保存 | チャットのメタデータはJSONで、汎用のメタデータ更新は部分マージです。 | 空間の定義は`chat.metadata.spatialContext`に置きますが、汎用のメタデータ更新ルートではなく、検証付きの専用エンドポイントを使います。 |

| オーナーターンの開始 | `/api/generate`は、表示用のGame状態を確定し、ユーザーメッセージを作り、その後に添付とペルソナのデータを別々の呼び出しで更新します。 | 小さなトランザクション境界を持つオーナーターンのサービスを追加し、ユーザーメッセージの作成と受け入れた空間移動が同時に成功または失敗するようにします。プロバイダーへの呼び出しはトランザクションの外に置きます。 |
| スワイプと分岐 | スワイプを削除するとGameスナップショットのインデックスがずれます。分岐を作るとGameとターンGameのスナップショットがすべて新しいメッセージIDへコピーされます。 | 空間スナップショットも両方の経路に参加し、より前の分岐点で有効だったスナップショットをコピーしなければなりません。 |
| プロンプトの組み立て | 実行時の生成、ドライラン、実行時のPeek Prompt、キャッシュされたPeek Prompt、GameのGMプロンプトは、それぞれ別の組み立て経路を持ちます。 | 構造化された空間データを一度だけ解決し、共有のフォーマッター/インジェクターをすべての実行経路から呼びます。キャッシュされたPeek Promptは、保存済みのプロバイダーリクエストをそのまま読み続けます。 |
| クライアントのデータ | サーバーのデータはReact Queryを使います。チャットごとの入力の下書きは画面遷移や再読み込みを越えて残ります。重いエディターは`AppShell`を通して遅延読み込みします。 | 専用のクエリー/ミューテーションのフックを追加し、保留中の遷移をチャットごとの下書きと並べて保持し、遅延読み込みのロケーションエディターを既存の詳細ビューの仕組みに載せます。 |

| 画像の一貫性 | 画像スタイルプロファイルがプロンプトのスタイルを決め、キャラクターとペルソナのアバターはすでに参照として送れます。受け付けられる参照の最大数はプロバイダーごとに異なります。ギャラリーは安定した画像IDをファイルパスとは別に保存しています。 | 場所の同一性を、全体のスタイルやキャラクターの同一性と切り分けます。該当する空間スナップショットを解決し、安定したギャラリー画像を対象となるシーンアートのリクエストにだけ添付し、既存のプロバイダーアダプターを通して候補を決定的に絞ります。 |
| 絵コンテの参照 | 絵コンテはすでに、キーフレームごとの登場キャラクターの計画、プロバイダーごとの参照上限の解決、プレビューと描画でのキャラクター画像の送信、元メッセージとスワイプの保存、描画済みキーフレームの動画1フレーム目としての利用を行っています。 | 凍結したビジュアル参照マニフェストを追加し、当時のロケーションを一度だけ解決し、キャラクターはキーフレームごとに変え、順序付きの選択を再生成の前後で保ちます。キーフレームから動画への入力は変更しません。 |

### 永続化の契約

定義はチャットのメタデータの中に残り、分岐がチャットのメタデータをコピーするときに自動でコピーされます。実行中の状態は別テーブルを使います。

```ts
interface SpatialContextSnapshotRow {
  id: string;
  chatId: string;
  messageId: string;
  swipeIndex: number;
  currentLocationId: string | null;
  definitionRevision: number;
  source: "bootstrap" | "owner_turn" | "assistant_swipe" | "definition_repair" | "branch_copy";
  transitionCommandId: string | null;
  transitionPayloadHash: string | null;
  createdAt: string;
}
```

必要なインデックスと不変条件:

- `(chatId, messageId, swipeIndex)`ごとに実効的な行は1つです。
- 遷移コマンドIDは、nullでない場合、そのチャットの中で一意です。
- 同じコマンドIDで移動先、想定リビジョン、想定される現在のロケーションが異なる場合は`409 spatial_transition_command_mismatch`を返します。
- 同じコマンドIDで内容も同じ場合は`409 spatial_transition_already_applied`を返し、確定済みのスナップショットとユーザーメッセージIDを含め、2度目の書き込みは行いません。クライアントはターンを送り直すのではなく、そのレスポンスから状態を合わせます。
- スナップショットの行は安定したロケーションIDを使います。名前の変更や親の付け替えでスナップショットが書き換わることはありません。
- 起動時の行は、確定したメッセージのアンカーができるまで`messageId: ""`とスワイプ`0`を使います。
- チャット、メッセージ、スワイプを削除すると、現在GameとターンGameのスナップショットを管理しているのと同じ場所で、対応する空間の行が削除またはずらされます。

新しいテーブルは、ファイルテーブルの定義、ファイルバックのテーブル一覧、カスケードのグラフ、プロファイルのバックアップ/復元、Mari DBの整合性メタデータに登録しなければなりません。参照時の挙動は、ファイルネイティブのリグレッションで確認します。

### 実効状態と履歴の規則

API、プロンプト、分岐、クライアントへのレスポンスで、1つのリゾルバーを使います。

1. 特定のメッセージとスワイプが指定された場合は、その空間スナップショットを返します。
2. 現在の表示に対しては、最後に見えているアシスタントメッセージとその有効なスワイプを調べます。
3. そのアシスタントのスワイプに行がない場合は、表示上のメッセージ順で最も近いユーザーターンまたはアシスタントのスナップショットまでさかのぼります。
4. それでもなければ起動時の行にフォールバックします。
5. スナップショットが1つもなく、有効な定義に妥当な開始ロケーションがある場合は、メモリー上の開始状態を返し、最初のオーナーターンでそれを実体化します。

オーナーターンのアンカー付け:

- 永続化の前に、タイムスタンプだけで最新の行を選ぶのではなく、現在表示されている履歴から元となる状態を解決します。
- 不可分なターンのトランザクションの中で、ユーザーメッセージ、最初のスワイプ、チャットのタイムスタンプ、そしてそのユーザーメッセージに紐づく`owner_turn`の空間スナップショットを作ります。
- アシスタントの応答を保存した後、その`(messageId, swipeIndex)`に同じ状態を`assistant_swipe`として実体化します。
- プロバイダーへの呼び出しが失敗または中断しても、受け入れたユーザーターンとその空間スナップショットは確定したままです。そのため再読み込みすると、アシスタントの応答をでっち上げることなく、移動と保存済みのユーザーメッセージが表示されます。
- 再生成では、対象のアシスタントメッセージの直前の状態を解決し、それを新しいスワイプに書き込みます。続きの生成では対象のスワイプの状態をそのまま使います。
- スワイプを選ぶと、既存の有効スワイプの行を通じて実効状態が変わります。他のスナップショットが書き換わることはありません。
- 分岐の作成では定義をコピーし、コピーしたすべての空間スナップショットを新しいメッセージIDに振り直し、起動時の行も含めます。前のメッセージで分岐する場合は、選んだ区切りでコピーを止めます。
- Gameのチェックポイントは、該当する空間スナップショットのIDか、その現在のロケーションと定義リビジョンの安定したコピーを保存します。チェックポイントを読み込むと、Gameの状態と空間の状態の両方が復元されます。

定義の編集は履歴を持ちません。名前の変更や親の付け替えを行うと、安定したロケーションIDがその分岐の現在の定義に対して解決されるため、古いスナップショットに表示されるパンくずリストも変わります。古いスナップショットがアーカイブ済みのロケーションを指すことはあります。その場合も読むことはできますが、次の移動先はアクティブで到達できるノードでなければなりません。エディターが現時点で実効的なロケーションをアーカイブする場合は`replacementCurrentLocationId`が必須で、サーバーは新しい定義リビジョンと同じトランザクションの中で、現在表示中のアンカーに`definition_repair`のスナップショットを書きます。

### 不可分なオーナーターンの手順

`generateRequestSchema`とクライアントの生成契約を、任意の`pendingSpatialTransition`で拡張します。これはRoleplayとGameのオーナーチャットでのみ受け付けます。

サーバー側の手順は次のとおりです。

1. 既存のチャットごとの生成ロックを取得します。
2. リクエストを解析し、リクエストのライフサイクルの中でチャットを読み込みます。
3. 空間の遷移がなければ、これまでのメッセージの流れを保ちます。
4. 遷移がある場合は、一定サイズのデータベーストランザクションを開始します。
5. トランザクションの中で定義と表示中の状態を読み直します。
6. オーナーモード、有効かどうか、想定される定義リビジョン、想定される現在のロケーション、コマンドID、移動先の状態、到達可能性を検証します。
7. トランザクションに紐づいたチャットストレージのインスタンスを通して、ユーザーメッセージと最初のスワイプを作ります。
8. 空間スナップショットを挿入し、チャットのタイムスタンプを更新します。
9. Gameの場合は、可能な範囲で同じトランザクションの中で表示用のGameスナップショットを確定します。
10. コミットした後、添付の付加処理、ペルソナのスナップショット、プロンプトの組み立て、プロバイダーへの処理をトランザクションの外で続けます。

検証の失敗は、クライアント側の楽観的な状態が正として扱われる前に起こります。`400`のグラフまたは移動先のエラーと、`409`の状態が古いというエラーには、安定した機械可読コード、利用者に見せても安全な文言、現在のリビジョン、現在のパンくずリストを含めます。非表示または通行不可の移動先の名前を含めることはありません。

クライアントは、サーバーがターンを受け入れるまで、送信したテキスト、添付、保留中の移動先を保持します。競合が起きた場合は楽観的に表示したメッセージを取り消し、Spatial Contextのクエリーを再取得し、下書きを復元して`Review destinations`を提示します。受け入れられた場合は3つをまとめて解除します。

### 共有プロジェクションの契約

リゾルバーは、プロンプト文が作られる前に構造化されたデータを返します。

```ts
interface ResolvedOwnerSpatialProjection {
  kind: "owner";
  chatId: string;
  ownerMode: SpatialOwnerMode;
  definitionRevision: number;
  currentLocationId: string;
  breadcrumb: Array<{ id: string; name: string }>;
  description: string;
  modelMemory: string | null;
  lorebookEntryIds: string[];
  destinations: Array<{ id: string; name: string; label?: string }>;
  omittedDestinationCount: number;
}

interface ResolvedLocationVisualProjection {
  chatId: string;
  messageId: string | null;
  swipeIndex: number | null;
  locationId: string;
  breadcrumb: Array<{ id: string; name: string }>;
  visualIdentity: string | null;
  references: Array<{
    imageId: string;
    role: LocationVisualReferenceRole;
    usageNote: string | null;
    sourceLocationId: string;
    inherited: boolean;
  }>;
}

interface StoryboardVisualReferenceCandidate {
  imageId: string;
  source: "explicit" | "location" | "character" | "persona" | "inherited_style";
  entityId?: string;
  label: string;
  role: string;
  order: number;
}

interface StoryboardKeyframeReferencePayload {
  keyframeIndex: number;
  imageIds: string[];
  omitted: Array<{
    imageId: string;
    reason: "provider_limit" | "not_visible" | "missing" | "setting_disabled";
  }>;
}

interface StoryboardVisualReferenceManifest {
  sourceMessageId: string;
  sourceSwipeIndex: number;
  locationId: string | null;
  definitionRevision: number | null;
  provider: string;
  model: string;
  providerReferenceLimit: number;
  status: "ready" | "needs_review";
  candidates: StoryboardVisualReferenceCandidate[];
  keyframes: StoryboardKeyframeReferencePayload[];
  createdAt: string;
}
```

プロンプトの上限は、保存の上限とは別物です。

- パンくずリストのノードは最大20個。
- オーナー向けの説明は最大4,000文字。
- モデル向けの非公開の記憶は最大8,000文字。
- 移動先は最大50件。`sortOrder`、名前、IDの順で決定的に並べ、その後に省略件数だけを付けます。
- 現在のロケーションのロアブック参照は、ロアブック処理がエントリー数とトークンの予算を適用する前の段階で最大50件。
- 保存できるビジュアル参照は1ロケーションあたり最大6件で、通常のシーンのリクエストでは、プロバイダー全体の参照上限を適用する前の段階でロケーション参照の候補が最大2件。
- 絵コンテのマニフェストは、監査と更新のために解決したすべての候補IDを保持してかまいませんが、キーフレームごとのペイロードは、マニフェスト作成時に記録したプロバイダーの上限で必ず抑えます。
- 連携用の`awarenessSummary`、またはその代わりの公開説明の抜粋は最大1,000文字。

1つのフォーマッターが、共有の構造化されたオーナーブロックを作ります。RoleplayとGameは、そのブロックの周りで薄いアダプターを使います。フォーマッターが`lorebookEntryIds`をシリアライズすることはありません。オーナープロンプトのパイプラインが、ロアブック処理を通してそれらを利用します。2つ目のフォーマッターはPhase 3でのみ導入し、プライバシーを削ぎ落としたConversation向けのブロックを作ります。こちらはロケーションロアの項目を受け取りません。

実行時の経路はすべて、最終的なモデルリクエストの準備の直前に、同じリゾルバーとフォーマッターを呼びます。

- 通常のRoleplayの生成。
- GameのGM生成。
- `/api/generate/dryRun`。
- 保存済みのリクエストが存在しないときの、実行時のPeek Promptの組み立て。
- プロンプトを組み立て直す再試行と続きの生成の経路。

キャッシュされた正確なPeek Promptには、新たな組み立ては不要です。保存済みのプロバイダーリクエストを表示するもので、そこにはそのスワイプで使われた空間ブロックが含まれていなければなりません。リグレッションでは、同じフィクスチャについて、実行時の生成、ドライラン、実行時のPeek Promptの空間ブロックを正規化して比較する必要があります。

### ロアブックを根拠にした下書きの契約

マップの根拠付けは、明示的な制作時の入力です。

```ts
interface SpatialMapGroundingRequest {
  mode: "setup_only" | "lore_strict" | "lore_expand";
  lorebookIds: string[];
  entryIds?: string[];
}
```

Gameのセットアップでは、`lorebookIds`のデフォルトを`GameSetupConfig.activeLorebookIds`から取ります。Roleplayでは、チャットで有効なグローバル、連携済み、固定済みのロアブックからデフォルトを取ります。制作者は生成の前に選択を変更できます。無効化されたロアブックとエントリー、明示的に除外されたロアブックとエントリーは、決して送りません。

これはロアブックの発動走査ではありません。サーバーは選ばれた出典を直接読み、オーナーのセットアップ情報に対して対応するマクロを解決し(解決後のテキストは保存しません)、次を含むカタログを作ります。

- 一時的な出典キー
- エントリー名とロアブック名
- 発動用のキーとタグ
- エントリーの説明(ある場合)
- 説明がない場合は、長さを限った内容の抜粋

カタログの大きさは、エントリー100件、16,000文字、そしてセットアップ、システム、要求する出力の分を確保した後に残る接続のコンテキストのうち、最も小さいものに合わせます。優先順位は決定的です。

1. 明示的に選択された`entryIds`。
2. ロケーションらしいタグ、名前、キーを持つエントリー。
3. 説明が書かれているエントリー。
4. 残りのエントリーを、ロアブックとエントリーの安定した順序で。

エントリーが省略された場合、プレビューはその件数を示し、Refine sourcesを提示します。ロアブック全体が考慮されたかのように見せることはありません。

簡略化したモデル向けの計画では、提案される各ロケーションに一時的な出典キーを付けます。サーバーは未知のキーを拒否し、有効なキーを安定したエントリーIDへ対応付け、重複を取り除き、プレビュー用の出典情報を計算します。

- `Lore-backed`: 検証済みの出典エントリーが1つ以上ある。
- `Inferred`: 出典の素材から導いた関係や包含だが、それ自体は出典エントリーになっていない。
- `Added by AI`: そのノードを裏づける出典エントリーがない。

`lore_strict`は、検証済みの出典キーを持たないノードをすべて拒否します。`lore_expand`は推測と追加のノードを受け入れますが、見える形でラベルを付けます。有効な出典キーが示すのは出典があることであって、意味が正しいことではありません。制作者がApplyの前に読み違えた関係や名前に気づけるよう、プレビューは出典の抜粋を表示しなければなりません。

生成のエンドポイントは、正規化された下書きの定義と、生成されたロケーションIDをキーとする一時的な出典情報のマップを返します。Saveの後に残るのは`lorebookEntryIds`だけです。置き換えと拡張は既存の履歴保護をそのまま維持します。拡張は新しいノードに結び付けを足せますが、既存のロケーションや結び付けを書き換えることはできません。

### Gameとの互換性の境界

GameのチャットでSpatial Contextが有効なとき:

- `SpatialContextSnapshot.currentLocationId`が正です。
- Game状態の`location`は互換性のための投影にすぎません。
- Game状態のGETレスポンスとトラッカーのUIは、表示するロケーションとして解決済みのパンくずリストを受け取ります。
- World Stateエージェントの修正と、Gameトラッカーの手動修正は、単独で`location`を書き込めません。サーバーはその項目を落としてデバッグ診断を残すか、明示的な手動編集に対しては項目単位の競合を返します。
- 新しいGameスナップショットは、セッション履歴と既存のUIが読める状態を保つために、旧来の`location`の値へパンくずリストを写します。ただしプロンプトのコードは引き続き空間プロジェクションを読みます。
- Gameのマップ、グリッドのセル、ノードは、安定した階層ロケーションIDに明示的に結び付けられます。
- 結び付けられた移動先を選ぶと、構造化された保留中の空間遷移が作られ、移動の文章が挿入されることはありません。
- 結び付けのないセルとノードの移動は戦術的なもので、変わるのはパーティーの位置だけです。
- 結び付けられたロケーションに入ると、あればそのローカルマップが選ばれます。出るときは、あれば最も近い結び付けられた祖先のマップが選ばれます。
- 両方が見えている場合、UIは2つの仕組みを`Story location`と`Map position`としてはっきり区別してラベル付けします。
- Spatial Contextを無効にすると、空間の定義もスナップショットも削除せずに、旧来のGameのロケーションの動作へただちに戻ります。

ネガティブコントロールでは、モデルが出したGameのロケーション修正、トラッカーの手動編集、結び付けのないマップのクリックのいずれも`currentLocationId`を変えられないことを実証しなければなりません。ポジティブコントロールでは、有効な結び付け済みのクリックが通常の遷移バリデーターを通ることを実証します。

### オーナー側UIの契約

Chat Settingsには、RoleplayとGameにだけ、コンパクトな`Hierarchical Map`セクションを1つ追加します。ここには有効かどうか、現在のパンくずリスト、アクティブとアーカイブの件数、警告の件数、`Open Map Editor`を表示します。エディター全体をパネルに埋め込むことはしません。

ロケーションエディターは、既存の全画面エディターのルートに従います。

- デスクトップでは、階層ナビゲーター、ローカルマップまたはレイヤー表示、選択中のロケーションのインスペクターを使います。
- モバイルでは階層を先に、詳細を後に表示し、ロケーション一覧へ戻る操作を見える形で置きます。ホバーやドラッグに依存する操作はありません。
- 各行には、子の追加、兄弟の追加、親の付け替え、サブツリーの複製、アーカイブ、リンクの操作を、ラベル付きのコントロールで用意します。
- ローカル表示では、子を座標付きのマップノード、順序付きのレイヤー、アクセシブルなリストのいずれかで描画します。
- 選択するとロケーションをプレビューし、移動は別の**Enter**操作で行います。
- インスペクターには、名前、種別、公開説明、モデル向けの非公開の記憶、アイコン、表示方法、配置またはレイヤー順、状態、親、直接リンク、紐づくロアを置きます。
- ビジュアルアイデンティティは、操作をさえぎるウィンドウではなくインスペクター内のセクションです。まず主画像のプレビューを見せ、続いて補助参照、役割、使いどころのメモ、継承の状態、壊れた状態、画像の出所のメタデータを表示します。
- ギャラリーの選択とアップロードは既存の画像コントロールを再利用します。`Generate establishing reference`はプレビューを開き、画像を受け入れる操作と主画像に設定する操作は明示的に行います。
- 生成されたシーンには、既存の画像操作から`Set as location reference`を提示します。そこで生成されたというだけでロケーションが書き換わることはありません。
- 紐づくロアは、操作をさえぎるウィンドウではなく、インラインの検索できる開閉領域を使います。結果はロアブックごとにまとめ、添付の前に無効や除外の状態を示します。
- 添付された行にはOpen entryとDetachを用意します。Detachでロアが削除されることはなく、サブツリーの複製では結び付けもコピーされます。
- ロアブックエディターには現在のチャットのマップからの被参照を表示するので、エントリーを使っているロケーションをすべて見つけられます。
- AIの下書きのコントロールには、出典のロアブック、グラウンディングのモード、考慮したエントリー数と省略したエントリー数、出典情報を表示します。プロンプトの技術的な知識は不要です。
- 検証はインラインで行い、Saveの近くにもまとめて表示します。まとめの項目を選ぶと、該当するノードと欄にフォーカスが移ります。
- エディターはローカルの作業用コピーと、リビジョン付きのSave操作を1つ使います。`editorDirty`が画面遷移を保護します。サーバーとの競合が起きても作業用コピーは保たれ、Reload server versionかReview differencesを提示します。無条件の上書きはありません。
- 空の状態では最初の操作を教えます: `Create a starting location`。有効なアクティブの開始ロケーションができるまで、有効化はできません。
- 読み込み中の表示は、既存のエディターのスケルトンの語彙を使います。保存、競合、アーカイブ済み、非表示、通行不可、不正の各状態は、色に加えてテキストかアイコンでも示します。

オーナーのチャット画面は`SpatialContextRuntimeBar`を共有します。

- 保存済みのパンくずリストは、物語の内容を覆わずに入力欄の上か横に見えています。
- 移動先の選択では、親、子、直接リンクをラベル付きのグループで一覧し、決定的な順序を保ちます。
- 移動先を選ぶと、はっきりラベル付けされた保留中のチップが作られます。状態がすぐに動くことはありません。
- チップは解除でき、テキストの下書きと一緒にチャットの切り替えや再読み込みを越えて残ります。
- 送信内容は、テキスト、添付、あるいは保留中の移動先だけでもかまいません。遷移はリクエストのデータであり、表示されるメッセージ本文に追記されることはありません。
- 古くなった保留中の移動先は、競合の後も`Needs review`と表示されたまま残り、有効な移動先を選び直すか解除するまで消えません。
- 画面が狭いときは、パンくずリストを中央で省略し、現在のロケーション名は残したうえで、アクセシブルな開閉領域から全体のパスを見られるようにします。

エディターとランタイムのコントロールは既存のセマンティックなテーマトークンを使い、ダーク、ライト、SillyTavernのテーマに対応し、モバイルの主要操作では44pxのタッチ領域を確保し、フォーカスの表示を含めます。動きは150から250 msの状態遷移に限り、装飾のためだけにレイアウトを動かすことはありません。

### 移植性とライフサイクルの網羅

Marinara形式のチャットのエクスポートには、次を含めなければなりません。

- `marinara_metadata`に入れた現在の定義。
- 表示名ではなく、エクスポート時のメッセージの序数とスワイプの番号をキーにした空間スナップショット。
- 起動時のスナップショット(存在する場合)。

インポートでは、チャット、メッセージ、スナップショットのIDを新しく作り、定義の中のロケーションIDは保ちます。壊れたグラフをインポートした場合はSpatial Contextを無効にし、修復のために生の定義を残し、警告を返します。名前で黙って一致させたり、一部だけ有効にしたりすることはありません。

チャットのJSONLエクスポートでは、ロケーションからエントリーへのIDは定義の一部なので保たれますが、ロアブックの内容が黙って同梱されることはありません。インポートでは移行先のプロファイルに対して参照を解決し、見つからないエントリーを名前の一致に頼らず、修復できる警告として報告します。プロファイルのバックアップと復元では、空間の定義とロアブックのテーブルの両方を持ち運ぶので、参照は機能したまま保たれます。将来、明示的なキャンペーンパッケージで、プロファイルをまたいだ移植のために参照先のロアブックを同梱するかもしれません。

チャットのJSONLは、ロケーションから画像へのID、役割、使いどころのメモ、順序も保ちますが、画像のバイト列を埋め込むことはありません。インポートでは移行先のプロファイルに対してそれらのIDを解決し、見つからない画像を、パスやファイル名の一致に頼らず修復できる警告として報告します。プロファイルのバックアップと復元には、プロフィールギャラリーのレコードとファイルを含めます。将来、明示的なキャンペーンパッケージで`Include location images`を提供し、エクスポートの前に素材の件数、合計サイズ、ライセンスの注意を示すかもしれません。

既存の絵コンテのライフサイクルをエクスポートまたはコピーする場合、そのビジュアルマニフェストは、元メッセージの序数とスワイプ、解決されたロケーションID、候補の画像ID、キーフレームの順序を、バイト列を埋め込まずに保ちます。インポートではメッセージIDと絵コンテのIDを振り直し、移行先のプロファイルでギャラリーの画像IDを解決し、見つからない素材を`needs_review`にします。マニフェストのない旧来の絵コンテは、最初の再生成のときに、保存済みの元メッセージとスワイプから解決します。名前の一致やチャットの最新ロケーションにフォールバックすることはありません。

プロファイルのバックアップと復元には、`FILE_BACKED_TABLES`を通して新しいテーブルを含めます。チャットの削除、一括削除、完全削除、分岐の削除、スワイプの削除、メッセージの削除は、既存のカスケードとアプリ側の後始末の経路に従います。メタデータがなければSpatial Contextは無効という扱いなので、既存のチャットに先回りの移行は不要です。

### 作業パッケージとマージの順序

#### パッケージA: 中核となる契約と検証用スパイク

- 共有の型、スキーマ、純粋なグラフのヘルパー、上限、フィクスチャ、安定したエラーコードを追加します。
- ファイルネイティブのストレージに対して、一定サイズのトランザクションを検証する一時的な仕組みを追加します。`.test.ts`ファイルは残さないでください。
- 起動時、表示中のスワイプ、より前の分岐点、アーカイブ済みの過去の現在地、古い定義のフィクスチャで、状態リゾルバーを検証します。
- 浅いグラフ、深さ20、幅500、長文、リンク付きのグラフについて、プロジェクションの大きさを測定します。

ゲート: UIの作業を始める前に、グラフの意味づけ、プロジェクションの上限、スナップショットのアンカー、トランザクションの実現性が示されていること。

#### パッケージB: 定義APIとストレージ

- スキーマ、マイグレーション、ファイルバックの登録、ストレージアダプター、GET、リビジョン付きPUTを追加します。
- アーカイブ操作のための現在ロケーションの差し替えを追加します。
- 削除、スワイプのずらし、プロファイルのバックアップ/復元を接続します。
- リビジョンの競合、不正なグラフ、非表示のエラー、コマンドの再利用について、サーバーのリグレッションを追加します。

ゲート: 定義とスナップショットが両方のストレージバックエンドで往復でき、不正な書き込みが中途半端な状態を残さないこと。

#### パッケージC: オーナーターンと履歴の統合

- 生成リクエストを`pendingSpatialTransition`で拡張します。
- 不可分なオーナーターンの永続化と、アシスタントのスワイプへの実体化を追加します。
- 再生成、続きの生成、有効なスワイプ、分岐、Gameのチェックポイントを統合します。
- 定義とスナップショットについて、Marinara形式のチャットのエクスポート/インポートを追加します。

ゲート: 再読み込み、プロバイダーの失敗、スワイプの変更、前のメッセージでの分岐、インポート/エクスポート、チェックポイントの復元で、期待どおりのロケーションが解決されること。

#### パッケージD: プロンプトプロジェクションとGameの権限

- 構造化されたプロジェクションと、長さを限ったフォーマッターを追加します。
- 実行時の生成、GameのGM、ドライラン、実行時のPeek Prompt、再試行、続きの生成を統合します。
- Gameとの互換性の境界と、トラッカーのパンくずリスト表示を徹底します。
- プライバシーと、非アクティブなロケーションのネガティブコントロールを追加します。

ゲート: すべてのプロンプト経路が同じ空間ブロックを含み、無関係なロケーションのテキストが漏れず、Gameが競合する正のロケーションを維持できないこと。

#### パッケージE: マップブラウザーとエディター

- React Queryのフック、競合の対応付け、設定の概要、遅延読み込みのエディタールートを追加します。
- 階層、ローカルマップ、レイヤー、リスト、プレビュー、インスペクター、サブツリーの複製の各操作を追加します。
- アクセシブルなデスクトップとモバイルの状態を追加します。
- リビジョンの競合をまたいで未保存の編集を保ちます。

ゲート: 制作者が、ドラッグ、ホバー、細かい操作なしで入れ子のマップを構築・修復できること。

#### パッケージE.1: AIによるマップ下書きの支援

- セットアップ時の情報を範囲を限って使い、必要なときだけ動く生成機能を追加します。ターンの途中で暗黙に書き換えることはしません。
- 簡略化したキー付きのマップ計画を生成し、その後に安定したIDを割り当て、安全な範囲でレイアウトの欠落を補い、完全な定義をサーバー側で検証します。
- 生成された階層は、エディターの状態を置き換える前にローカルの下書きとしてプレビューします。
- ApplyとSaveの明示的な操作を必須にします。生成そのものがSpatial Contextを有効にしたり定義を書き込んだりすることはありません。
- 通常のチャット履歴は生成プロンプトに入れず、最終的なプロンプトはデバッグログで確認できるようにします。

ゲート: 技術に詳しくない制作者が、世界を説明し、妥当な入れ子のマップを受け取り、内容を確認し、Saveまで永続化された状態を変えずに却下または適用できること。

#### パッケージE.1.1: 履歴を壊さないAIによるマップ拡張

- マップ全体のAI生成は、キャンペーン開始前の作業として扱います。メッセージに紐づく空間の履歴ができた後は、既存のロケーションIDをサーバー側ですべて保ちます。
- 進行中のキャンペーンでは、全体生成の代わりに、選んだアクティブなロケーションに範囲を絞った追加のみの拡張を使います。
- 現在のロケーション、開始ロケーション、既存の説明、リンク、レイアウト、アーカイブ済みのノード、今後のGameの結び付けを保ちます。新しい安定したIDは、追加されたロケーションにだけ割り当てます。
- 拡張は、通常のターン履歴ではなく、範囲を限ったセットアップと選択中のロケーションの情報にもとづいて行います。
- 新しいロケーションはローカルの下書きとしてプレビューし、既存のApplyとSaveの境界を保ちます。
- マップ全体の置き換えは、確定した空間の履歴ができる前にだけ許可します。すでにマップがある場合は、拡張のほうが安全なデフォルトです。

ゲート: AIが、ターンのスナップショットを孤立させず、現在のロケーションを変えず、既存のIDを置き換えずに、進行中のキャンペーンのマップを広げられること。

#### パッケージE.2: Gameの設定ウィザードのマップ選択

- 既存のFeaturesステップに、任意の`Draft a hierarchical world map`という選択肢を、簡単な規模の選択とあわせて追加します。
- マップの生成は、`/game/setup`が世界の概要と物語の筋書きを保存した後にだけ実行します。プレイのターンは不要です。
- 後続の下書きを生成しているあいだ、セットアップが処理中であることを見える形で保ちます。修復されたセットアップのペイロードを適用した後も同様です。
- 生成後は、通常のAIプレビューとマップエディターを開きます。Skipでゲームに戻り、Applyは作業用コピーだけを変え、永続化の境界は引き続きSaveです。
- マップの生成に失敗した場合は、正常に作成できたゲームを保ち、失敗の内容を説明し、後からChat Settingsでマップを作れるようにします。
- 狭い設定ウィザードにマップエディター全体を埋め込んだり、生成した定義を黙って有効にして保存したりしてはいけません。

ゲート: 制作者が、途中までのウィザードの状態から生成したりレビューを飛ばしたりすることなく、セットアップ中により充実した初期マップを求められること。

#### パッケージF: RoleplayとGameのランタイムUI

- 共有のランタイムバーと、チャットごとの保留中の遷移の保持を追加します。
- 表示されるメッセージ本文を変えずに、RoleplayとGameの送信経路を統合します。
- Gameのマップ、セル、ノードの明示的な結び付けのコントロールを追加します。
- 遷移が受け入れられたら結び付けられたマップを選び、結び付けのない戦術移動は保ちます。

ゲート: RoleplayとGameで、移動、古い状態からの復帰、再読み込み、チャットの切り替えができ、キーボードとタッチでこの機能を使えること。

#### パッケージF.1: ロケーションとロアブックの結び付けとランタイムの発動

- 共有スキーマとエディターの作業用コピーを、長さを限った`lorebookEntryIds`で拡張します。
- インラインのマップ添付のコントロール、ロアブックからの被参照、壊れた参照の警告を追加します。
- 共有のロアブック処理を、強制候補のID、発動元の重複排除、除外、ロケーションロアの予約上限で拡張します。
- 同じリゾルバーを、Roleplay、GameのGM、ドライラン、実行時のPeek Promptの経路に統合します。
- Active Contextに発動元と切り詰めの報告を追加します。
- 分岐とJSONLのエクスポート/インポートの流れを通して参照IDを保ち、移行先にロアがない場合は警告します。

ゲート: ロケーション間を移動すると、すべてのオーナープロンプトの経路で移動先の有効な添付ロアだけが発動し、二重挿入もConversationへの漏れも起きないこと。

#### パッケージF.2: ロアブックを根拠にしたマップの下書き

- 作成、置き換え、拡張の各リクエストに、グラウンディングのモードと明示的な出典選択を追加します。
- 通常のチャット走査ではなく、選ばれたロアブックから、範囲を限った出典カタログを作ります。
- 一時的な出典キーを検証し、有効なエントリーを生成されたノードへ自動で結び付けます。
- 下書きのプレビューで、Lore-backed、Inferred、Added by AIの出典情報と、出典の確認手段を表示します。
- Strict canonでは出典のあるノードだけを許し、Canon with expansionでは根拠のない追加を見える形にします。
- 履歴を壊さない追加のみの拡張と、既存のApplyからSaveへのレビュー境界を保ちます。

ゲート: 選んだロアブックの事実が生成された階層を直接根拠づけ、根拠のないロケーションがSaveの前にすべて見え、厳密モードでは出典のないノードを永続化できないこと。

#### パッケージF.3: ロケーションのビジュアルアイデンティティとシーンアートの参照

- 長さを限ったビジュアルアイデンティティのテキストと、安定したプロフィールギャラリーの結び付けを、ロケーションのスキーマとエディターの作業用コピーに追加します。
- インラインのビジュアルアイデンティティ編集、主参照と補助参照の役割、明示的なスタイルの継承、ギャラリーからの被参照、壊れた参照の修復を追加します。
- チャットごとのIllustratorとGameのプロバイダー利用のコントロールを、対になる形で追加します。最初の主画像での同意を必須にし、後方互換のためデフォルトはオフにします。
- 必要なときに全景の参照画像を生成する仕組みと、レビュー済みの生成シーンを明示的に昇格する操作を追加します。
- RoleplayのIllustratorとGameのシーンアートのリクエストで、該当するメッセージとスワイプのロケーションを解決します。
- 明示的な参照、ロケーション、キャラクター、ペルソナ、継承されたスタイルの候補を、プロバイダーごとの既存の上限のもとで決定的に統合し、除外の理由を見える形にします。
- 分岐とJSONLを通してIDとメタデータを保ち、プロファイルのバックアップと復元にバイナリを含め、物語プロンプトとConversationのネガティブコントロールを追加します。

ゲート: 同じロケーションで繰り返しアートを作るときにレビュー済みの場所の同一性を再利用でき、キャラクター参照とのトレードオフが決定的かつ見える形で示され、過去のメッセージのアートが当時のロケーションを解決し、ビジュアル専用のデータがテキストプロンプトへ漏れないこと。

#### パッケージF.3.1: 絵コンテのビジュアル参照マニフェスト

- F.3.1はF.3の下流の利用者かつ独立してレビューできる変更として保ちます。F.3の永続化のゲートを広げるものではありません。
- 絵コンテのメタデータに、凍結した参照バンクと、キーフレームごとの順序付きペイロードのマニフェストを追加します。
- ロケーションの解決を絵コンテの元メッセージとスワイプに固定し、同じ場所の候補をそのフレーム全体で再利用します。
- キャラクターとペルソナの参照は各キーフレームの登場キャラクターの一覧から選び、画面に映らない出演者に容量を使いません。
- 明示的、枠1つ、枠複数、補助、継承スタイルの優先順位を、既存のプロバイダー能力のリゾルバーを通して決定的に適用します。
- プレビューと再生成に、段階的なVisual sources、除外の理由、レビューが必要な競合、明示的なRefresh referencesを追加します。
- Spatial Contextが無効な場合や、対象となるロケーション参照がない場合は、これまでの絵コンテの動作を保ちます。

ゲート: キーフレームを再生成すると凍結したペイロードが再利用され、ロケーションとキャラクターの選択が当時のとおりで内容を確認でき、プロバイダーの許容量を変えても既存の絵コンテが黙って変わらないこと。

#### パッケージG: 連携したConversation

- パッケージAからF.3.1までが安定してから実装します。
- 生成時にリンク先のオーナーを解決し、削ぎ落とした形のプロジェクションフォーマッターを使います。
- 控えめな在席の言い回しと、読み取り専用のUIを追加します。
- リンク解除、再リンク、オーナーの削除、壊れた相互リンク、ループ、完結した物語の挙動を実証します。

ゲート: Conversationが、モデル向けの非公開の記憶、内部ID、非表示の移動先、ロケーションに添付されたロアのIDと内容、ロケーションのビジュアル参照のIDと内容、変更の権限のいずれも受け取らないこと。

モデルからの移動要求、制作者向けテンプレート、持ち運べるキャンペーンパッケージ、画像からのマップ推測、全ロケーション分の参照アートの一括生成、複数視点のキャラクター参照の自動選択、キャラクターごとの位置は、オーナー側の根拠付け、ビジュアルアイデンティティ、絵コンテのマニフェストの作業を出した後の、別のパッケージに残します。

### IssueとPull Requestの区切り

これはリポジトリーのワークフロー上、大きな機能です。パッケージAの実装を始める前に:

1. 追跡用のIssueを1つ確認するか新しく作り、そこで担当を見える形にします。
2. Issueに紐づく既存のブランチ、ドラフトのPull Request、プロジェクトボードの項目がないか確認します。
3. 実装を始めたらすぐに、`staging`に対してドラフトのPull Requestを開きます。
4. 可能な範囲で、作業パッケージをレビューしやすいPRの区切りとして使います。PRの数を減らすためだけに、オーナーMVPと連携したConversationをまとめてはいけません。

推奨するIssueの分割:

1. Spatial Contextの共有コア、永続化、定義API。
2. オーナーターンのスナップショット、スワイプ、分岐、チェックポイント、移植性。
3. オーナー側のプロンプトプロジェクションとGameとの互換性。
4. オーナー側のエディターと実行時の移動のUI。
5. ロケーションとロアブックの結び付けと、オーナー側の実行時の発動。
6. ロアブックを根拠にしたマップの下書き。
7. ロケーションのビジュアルアイデンティティとシーンアート参照の解決。
8. 絵コンテの凍結したビジュアル参照マニフェスト。
9. 連携したConversationの読み取り専用プロジェクション。
10. モデルからの移動要求。

## 受け入れ基準

- マップのロケーションはロアブックのエントリー参照を保存し、ロアの内容をコピーして持つことはありません。
- ロケーションは任意のビジュアルアイデンティティのメタデータと、安定したギャラリー画像の参照を保存します。生のパス、外部URL、画像のバイト列は保存しません。
- 描画スタイルは画像スタイルプロファイルが決め、場所の同一性はロケーション参照が決め、被写体の同一性はキャラクターまたはペルソナの参照が決めます。
- 対象となるシーンアートのリクエストは、過去にさかのぼる再生成も含めて、そのメッセージとスワイプの厳密なロケーションを解決し、名前による曖昧な一致は行いません。
- 生成されたアートは、制作者の明示的な操作があって初めてロケーションの参照になります。
- layoutの参照が通常のシーン生成に自動で入ることはなく、子孫へ継承できるのはstyleの参照だけです。
- テキストのプロンプトと連携したConversationは、ロケーションのビジュアル参照のID、バイト列、パス、画像専用のメモを受け取りません。
- 絵コンテは元メッセージとスワイプからロケーションを解決し、参照バンクと順序付きのキーフレームのペイロードを凍結し、明示的な更新まで再生成でそれらを再利用します。
- 絵コンテのキーフレームはそれぞれ、解決されたロケーションと登場する人物についてのみ参照を選びます。画面に映らない出演者が容量を使うことはありません。
- 枠が1つのプロバイダーと複数のプロバイダーの挙動は決定的で目に見え、プロバイダーの変更が凍結した参照を黙って追加、削除、置換することはありません。
- 絵コンテのマニフェストは安定したIDとメタデータを保存し、画像のバイト列やファイルシステムのパスは保存しません。
- マニフェストのない旧来の絵コンテが、ロケーション名の一致やチャットの最新ロケーションを暗黙の修復手段として使うことはありません。
- 添付されたロアを強制的に発動させるのは、受け入れられた厳密な現在のロケーションだけであり、無効化、除外、重複排除、順序、エントリー数の上限、トークンの予算の規則に従います。
- Active Contextは、現在のロケーションによる発動、複数の発動元の組み合わせ、決定的な切り詰めを示します。
- 根拠付きの下書きは、キーワードの走査や生成された世界の概要に頼らず、明示的に選ばれたロアのエントリーを直接読みます。
- Strict canonは出典のあるロケーションだけを作り、Canon with expansionはSaveの前に、推測または根拠のない追加をすべてラベル付けします。
- 連携したConversationは、ロケーションに添付されたロアのIDも内容も受け取りません。
- 名前の変更と親の付け替えを行っても、ロケーションの同一性は保たれます。
- 不正なグラフと古い書き込みが状態を変えることはありません。
- 移動はユーザーターンと一緒に確定するか、まったく確定しないかのどちらかです。
- 再読み込み、スワイプの選択、前のメッセージでの分岐、Gameのチェックポイントの復元で、正しいロケーションが解決されます。
- オーナーのプロンプトには、アクティブなロケーションの情報と有効な移動先だけが含まれます。
- 有効なとき、Gameが競合する自由記述のロケーションを表示したりプロンプトに使ったりすることはありません。
- 既存のGameのマップは、戦術移動を壊さずに階層のロケーションへ明示的に結び付けられます。
- RoleplayとGameは同じ階層と遷移の規則を使います。
- ドライランとPeek Promptは、生成と同じプロジェクションの挙動を使います。
- 既存のチャットと、Spatial Contextが無効な場合は、これまでの挙動が保たれます。
- Conversationが空間の状態を所有したり変更したりすることはできません。
- モデル向けの非公開の記憶がConversationのプロジェクションに入ることはありません。

## 検証

決定的に網羅すべき対象は、グラフの上限、ループ、移動の方向、非表示と通行不可のリンク、古いリビジョン、冪等性、分岐点、スワイプ、チェックポイント、ロアブックの参照上限、強制発動、除外、重複排除、トークンの切り詰め、根拠付けのカタログの上限、出典キーの検証、厳密モードでの拒否、出典情報、ビジュアル参照の上限、主参照と継承の規則、過去のビジュアルの解決、プロバイダーによる絞り込み、見つからない画像の警告、リクエスト種別による除外、絵コンテの元への固定、凍結したマニフェストでの再生成、登場キャラクターによる絞り込み、枠1つと枠複数の選択、プロバイダーの許容量の変化、明示的な更新、旧来のマニフェストへのフォールバック、プライバシーの境界、非アクティブなロケーションのネガティブコントロールです。

リポジトリーのチェック:

```bash
pnpm check
pnpm regression:prompt
pnpm smoke:ui
```

手動での確認は、デスクトップとモバイルでの制作、深いパンくずリスト、レイヤー、座標付きのマップ、長い名前、競合からの復帰、アーカイブの保護、Roleplay、Game、結び付けありとなしのマップ移動、再読み込み、分岐、チェックポイントの復元、紐づくロアの添付と被参照、無効なロアと壊れたロア、出典が多いときの省略警告、Strict canonとCanon with expansionのプレビュー、画像のアップロードとギャラリー選択、主参照と補助参照、シーンの明示的な昇格、継承されたスタイル、壊れた画像、プロバイダーの除外の報告、過去のスワイプのアート、絵コンテのVisual sources、枠1つと枠複数のプロバイダー、凍結した状態での再生成、プロバイダー変更時のレビュー、明示的な更新、旧来の絵コンテ、Active Context、Peek Promptを対象にします。PRの検証チェックボックスは、人が確認するために未チェックのままにします。

- プロバイダーごとの合成参照やコンタクトシートの生成
