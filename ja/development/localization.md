# UIのローカライズ

Marinara Engineはアプリの画面テキストをローカライズします。モデルへ送るプロンプト、作成したコンテンツ、生成されたチャットの
本文、識別子、プロトコルの値、ファイルパス、保存済みの機械向けの値は変更しません。

英語が正規のロケールであり、実行時のフォールバック先でもあります。コミュニティ翻訳が欠けている箇所には、翻訳キーや空の
コントロールではなく英語のテキストが表示されます。

画面の言語は**Settings > General > App Behavior > Language**(設定 > 一般 > アプリの動作 > 言語)で選びます。切り替わるのは
Marinaraの操作画面と説明文だけで、モデルへのプロンプト、作成したコンテンツ、チャットのメッセージは変わりません。

## 対応している画面の言語

| 言語 | ロケールファイル | 文字の方向 |
| --- | --- | --- |
| アラビア語 | `ar.json` | 右から左 |
| 中国語(簡体字) | `zh-Hans.json` | 左から右 |
| 英語 | `en.json` | 左から右 |
| フランス語 | `fr.json` | 左から右 |
| ドイツ語 | `de.json` | 左から右 |
| ヒンディー語 | `hi.json` | 左から右 |
| 日本語 | `ja.json` | 左から右 |
| 韓国語 | `ko.json` | 左から右 |
| ポーランド語 | `pl.json` | 左から右 |
| ポルトガル語(ブラジル) | `pt-BR.json` | 左から右 |
| ロシア語 | `ru.json` | 左から右 |
| スペイン語 | `es.json` | 左から右 |

英語のカタログをソースとして管理します。同梱されている他のカタログは機械翻訳を出発点としており、その言語に堪能な方からの
修正を歓迎します。UIからの文字列の抽出はまだ途中なので、翻訳キーが用意されていないテキストは英語のまま表示されます。

## ロケールファイル

クライアントのロケールファイルは次の場所にあります。

```text
packages/client/src/localization/locales/
```

BCP-47のロケールはそれぞれ、正規のロケール名を付けたJSONファイル1つで表します。たとえば`pl.json`、`ko.json`、
`pt-BR.json`です。Viteがこれらのファイルを自動的に見つけるため、ロケールを追加してもレジストリーを編集する必要はありません。
英語はアプリと一緒に読み込まれ、他のロケールは選択されたときにだけ読み込まれます。

```json
{
  "_meta": {
    "locale": "pl",
    "direction": "ltr"
  },
  "chat.input.placeholder": "Napisz odpowiedź…",
  "common.actions.save": "Zapisz"
}
```

キーは画面の領域ごとに整理した意味ベースの名前にします。英語の文そのものをキーにしないでください。ふつうの文言修正のたびに、
すべての翻訳が無効になってしまいます。

## 翻訳のルール

- 翻訳するのは値だけです。意味ベースのキー名は変更しません。
- `{{name}}`のような補間トークンと、`<strong>`のようなリッチテキストのタグはそのまま残します。
- 翻訳キーはアルファベット順に並べたままにします。
- Marinara Engineのような製品名は変更しません。プロジェクトが公式の訳名を採用した場合だけ例外です。
- `en.json`の意味とトーンに合わせます。英語の原文にない動作や約束を足さないでください。
- 訳したラベルがデスクトップでもモバイルでも収まるか確かめます。

機能領域の翻訳を準備している間、コミュニティのロケールでは一部のキーが一時的に欠けていてもかまいません。欠けたキーは英語に
フォールバックします。未知のキー、空の翻訳、壊れたメタデータ、変更された補間トークンがあると、ローカライズのチェックは失敗します。

機能のPRでは正規の英語キーを追加または更新する必要がありますが、コミュニティの全ロケールに手を入れる必要はありません。
コミュニティの値を訳すのは、貢献者が役に立つ翻訳を用意できるときだけです。キーの一覧をそろえるためだけに、英語の値を各ロケール
ファイルへコピーしないでください。実行時のフォールバックが同じ英語テキストを表示しますし、キーを空けたままにしておけば翻訳者に
不要なマージ衝突が起きません。

機械翻訳も、PRでそうだと明示するなら最初の下書きとして歓迎します。そのロケールをレビュー済みと呼ぶ前に、堪能な方が用語、トーン、
文字切れ、モバイルでのレイアウトを確認してください。

## 既存の翻訳への修正を提出する

小さな言い回しの修正なら、GitHubのWebエディターだけで足ります。

1. [`packages/client/src/localization/locales/`](../../packages/client/src/localization/locales/)でロケールファイルを
   開きます。
2. 鉛筆アイコンを選んでファイルを編集します。必要な場合はGitHubがフォークの作成を提案します。
3. 変更するのは訳文の値だけです。キー、`{{name}}`のような記号に敏感なトークン、JSONの構文はそのまま保ちます。
4. フォーク内の目的を絞ったブランチに変更をコミットします。
5. Marinara Engineの**`staging`**ブランチに対してプルリクエストを開きます。`main`ではありません。
6. PRの説明には、言語、修正した意味、そして自分が堪能な話者なのか機械翻訳を使ったのかを書きます。

タイトルは`Improve French UI translation`のような形にします。1つのロケールに対する関連した修正は、まとめて1つのPRにできます。
無関係なコード変更は分けてください。

## 新しいローカライズを提出する

新しい言語に取り組むときは、最新の`staging`ブランチから始めます。

```bash
git clone https://github.com/YOUR-NAME/Marinara-Engine.git
cd Marinara-Engine
git checkout staging
git pull
git checkout -b translation/LOCALE
pnpm install
```

続いて次の手順を行います。

1. `en.json`を、`it.json`や`pt-PT.json`のような正規のBCP-47ロケール名のファイルにコピーします。
2. `_meta.locale`は`.json`を除いたファイル名と同じにします。
3. `_meta.direction`に`ltr`または`rtl`を設定します。
4. 上のルールに従って値を翻訳します。新しいロケールでは英語カタログ全体を訳しきるのが望ましいものの、途中までのカタログでも
   残りは英語にフォールバックします。
5. ロケールの検証とリポジトリーの基本チェックを実行します。

   ```bash
   pnpm localization:check
   pnpm check
   ```

6. **Settings > General**で言語を選び、デスクトップとモバイルの両方で確認します。長いラベル、ツールチップ、読み込み中と
   エラーの表示、文字の方向をチェックします。
7. ブランチを自分のフォークへプッシュし、
   [プルリクエストを開きます](https://github.com/Pasta-Devs/Marinara-Engine/compare)。ベースには
   `Pasta-Devs/Marinara-Engine:staging`を選びます。

PRの説明には、ロケール、翻訳の出所、堪能さやレビューの度合い、実行した検証コマンド、そしてネイティブスピーカーの確認がまだ
必要な箇所を書きます。PRテンプレートは正直に埋め、自分で実際に確かめた手動の項目だけにチェックを入れてください。

## クライアントコードで翻訳を使う

Reactコンポーネントでは`useTranslation`を使います。

```tsx
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
return <button>{t("common.actions.save")}</button>;
```

モジュール階層のUI設定には、訳文そのものではなく翻訳キーを保存します。こうすると、ページを再読み込みしなくても言語の切り替えが
その場で反映されます。React以外のクライアント側のヘルパーは、`packages/client/src/localization/i18n.ts`がエクスポートする
`translate`関数を使えます。

画面に見えるテキストはすべて翻訳します。ラベル、プレースホルダー、ツールチップ、アクセシビリティー用の名前、代替テキスト、
読み込み中と空の状態、トースト、確認メッセージ、静的なチュートリアルが対象です。プロンプトや作成したコンテンツをUIの翻訳機構に
通してはいけません。

Settingsのコントロール、ヘルプのツールチップ、ウィンドウのタイトルといった共有の旧来の部品は、古い呼び出し箇所の移行が終わるまで、
正規の英語カタログの値と完全に一致する文字列も認識します。これは互換性のための橋渡しであって、推奨されるAPIではありません。
新規のコンポーネントや大きく手を入れたコンポーネントでは、意味ベースの`t("area.control.label")`キーを直接使ってください。
`en.json`にない英語の文は翻訳できません。

リポジトリーのローカライズチェックでは、クライアントのTSXに未翻訳の画面テキストが残っていないかも検査します。

```bash
pnpm localization:ui-check
```

対象は、表示されるJSX、直接埋め込まれたラベルや注意書き、アクセシブルな名前、プレースホルダー、読み込み中と空の状態、トースト、
確認メッセージです。`code`、`pre`、`script`、`style`の各要素の中にあるリテラルは意図的に除外しています。コマンド、設定、URL、
マクロなど機械向けの例をそのまま保つためです。動的に作成された値、生成された値、保存された値、プロンプトの値、プロトコルの値も
同様に、画面の翻訳機構の外に置く必要があります。

## ダウンロードして追加するエージェントの画面

Engineに同梱されているエージェントの画面は、Engineのロケールファイルを使います。ダウンロードして追加する機能クライアントは、
Marinara-Agentsリポジトリー内で自分の訳文を管理します。

機能のカスタム要素にはいずれも、選択中のロケールが`lang`属性と`dir`属性の両方で渡され、さらに次の値も渡されます。

```ts
capabilityProps.localization = {
  locale: "pl",
  direction: "ltr",
};
```

ロケールが変わると、既存の`marinara-capability-props`イベントが発生します。パッケージ側のUIは同梱のロケールを選び、
なければパッケージ内の英語にフォールバックし、このイベントの後に再描画してください。
