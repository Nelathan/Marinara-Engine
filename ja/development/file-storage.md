# ファイルネイティブストレージ

このガイドでは、Marinara Engineのローカル永続化アーキテクチャを説明します。利用者から見たフォルダー構成は[Marinaraがデータを保存する場所](../data/where-data-is-stored.md)を参照してください。

## 信頼できる唯一の保存先

Marinaraはアプリケーションの行データを、`DATA_DIR/storage`の下にJSONのスナップショットとして保存します。

```text
storage/
├── manifest.json
└── tables/
    ├── chats.json
    ├── messages.json
    ├── characters.json
    └── ...
```

`FILE_STORAGE_DIR`を指定すると`storage`ディレクトリーを上書きできます。各テーブルのファイルはJSON配列を1つ収めた形です。`manifest.json`には、ストレージ形式のバージョン、保存時刻、バックエンドの識別子、そして登録済みテーブルごとの行数が記録されます。

## 実行時のモデル

`packages/server/src/db/file-backed-store.ts`は、起動時にテーブルのスナップショットをメモリーへ読み込みます。サーバーはそれらの行を、`db/file-query.ts`が公開するファイルネイティブな操作を通じて読み書きします。`db/file-schema.ts`は、`db/schema/`にある定義に対して、衝突を避けたテーブルとカラムのメタデータを供給します。

`select`、`insert`、`update`、`delete`を連ねて書けるAPIのおかげで、ストレージ関連のサービスは小さくまとまり、外部のデータベースやORMにも依存しません。対応するフィルターと並び順は明示的な式オブジェクトで表すので、ストアがクエリー文字列を解析することはありません。

テーブルは`fileTable(..., { uniqueBy: [...] })`で自然キーを宣言します。挿入と更新では、メモリー上の行を書き換える前に、変更後の候補全体に対して主キーと宣言済みの自然キーを検証します。そのため制約に違反した場合でもテーブルはそのまま残ります。一意性が一部の行にだけ当てはまるときは、ルールに`when`の述語を含められます。

ダウンロードした機能パッケージが、独自のファイルテーブルのインスタンスを持っている場合もあります。ストアはオブジェクトの同一性を確認したうえで、登録済みのテーブル名からそれらのインスタンスを解決します。これにより、パッケージ側のストレージコードからEngineのテーブルを安全に扱えます。

## 永続化と復旧

書き込みが起きると、対象のテーブルにdirtyの印が付きます。短いデバウンスで近い時刻の変更をまとめ、さらに安全弁のタイマーが未処理の書き込みを定期的にフラッシュします。正常終了のときは、実行中の書き込みを待ってから、その書き込みの最中に変更された行も保存します。

各スナップショットは、いったん一時ファイルへ書き出してフラッシュし、アトミックにリネームします。置き換えの前には、直前の正常なスナップショットを`.bak`ファイルとして更新します。起動時に本体のファイルが読めなかった場合は、可能であればバックアップから復旧します。どちらも使えないときは、Marinaraが壊れたファイルにタイムスタンプ付きの接尾辞を付けて隔離し、そのテーブルだけを空にして起動します。復旧作業ができるように画面へ到達できる状態を保つためです。

## トランザクション

トランザクションは、`AsyncLocalStorage`でスコープを区切ったコピーオンライトのスナップショットを使います。テーブルが複製されるのは、そのトランザクションが最初にそのテーブルを書き換えた時点だけです。コールバックが例外を投げた場合、元に戻るのはそのトランザクションが変更したテーブルだけで、無関係な同時書き込みは残ります。

## テーブルを追加する

永続化するデータを追加するときの手順です。

1. `packages/server/src/db/schema/`に、`fileTable`とファイルネイティブなカラムビルダーでテーブルを定義します。
2. `db/schema/index.ts`からエクスポートします。
3. 自然キーがある場合は、テーブルオプションの`uniqueBy`で宣言します。
4. テーブル名を`FILE_BACKED_TABLES`に登録します。
5. 必要に応じて、カスケードやset-nullの関係を`file-backed-store.ts`に定義します。
6. テキストの項目に構造化されたJSONが入る場合は、`services/mari-db/mari-db.service.ts`にJSONカラムのメタデータを含めます。
7. プロファイルのバックアップと復元の動作を確認します。
8. `pnpm check`と、関係するストレージの回帰テストを実行します。

テーブル定義、リレーションのメタデータ、プロファイルの可搬性、Mari DBの検証は、同じ変更の中で足並みをそろえてください。
